# GoreeCloud Web Scraper

**Rebranded import of [D4Vinci/Scrapling](https://github.com/D4Vinci/Scrapling)**, based on the upstream `main` commit [`bc602488b44e978da3266841e913af17577ec0fd`](https://github.com/D4Vinci/Scrapling/commit/bc602488b44e978da3266841e913af17577ec0fd).

GoreeCloud Web Scraper is an attributed, independently maintained Python web scraping framework. Its imported foundation provides HTML parsing, HTTP fetching, optional browser-assisted fetching, spiders, and command-line tools. Importing the upstream code does not independently validate these capabilities in the GoreeCloud repository.

**Important:** This is a *rebranded import*, not an original codebase. Original code and copyright belong to the original authors and contributors. This downstream project is not affiliated with or endorsed by D4Vinci, Karim Shoair, or the Scrapling contributors.

## Installation from this repository

The imported framework requires Python 3.10 or later.

```sh
git clone https://github.com/GoreeCloud/web-scraper.git
cd web-scraper
python -m pip install -e .
```

For additional fetching, CLI, and browser capabilities, after reviewing optional dependencies and installation scripts:

```sh
python -m pip install -e ".[fetchers]"
goreecloud-web-scraper --help
```

The `goreecloud-web-scraper` and `goreecloud-web-scraper-mcp` entry points are downstream aliases. The existing Python import namespace (`scrapling`) and original CLI entry points (`scrapling`, `scrapling-mcp`) are **intentionally retained for compatibility**. The distribution metadata name is `goreecloud-web-scraper`; no release to PyPI or container registry is implied.

The new Python alias goreecloud_web_scraper delegates public entry points to the original implementation.

## Python example

```python
from goreecloud_web_scraper import Selector

page = Selector("<html><body><h1>Hello</h1></body></html>")
print(page.css("h1::text").get())
```

See the [original upstream README](UPSTREAM_README.md) for broader examples and optional installation instructions. The [upstream documentation](https://scrapling.readthedocs.io/en/latest/) describes the source foundation, not independent GoreeCloud release acceptance.

## Browser privacy defaults (development)

The inherited browser engine's earlier defaults allowed geolocation and notification permissions without consent, ignored HTTPS certificate errors and allowed service workers. GoreeCloud Web Scraper now defaults to `permissions=[]`, `ignore_https_errors=False`, and `service_workers="block"` for local and remote stealth browser contexts. These defaults are verified by offline CI tests. A caller who intentionally needs a sensitive capability can explicitly opt in with the existing `additional_args` settings, which should be scoped to an authorized use case.

Service-worker restrictions and a page-request interceptor are **not** general network isolation. A local development smoke can use the opt-in `scripts/browser_loopback_smoke.py` script with a reviewed browser executable and SHA-256, running against an owned temporary 127.0.0.1 server. Run it only in an approved isolated development environment with `GOREECLOUD_BROWSER_EXECUTABLE` and `GOREECLOUD_BROWSER_SHA256` provided for the exact reviewed executable. This browser probe is not part of the hosted CI matrix and is not evidence of safe arbitrary web browsing. **Chromium sandbox is now requested by default** for locally launched browser sessions (`chromium_sandbox=True`, supported by Patchright/Playwright). If the operating system or browser cannot provide a working sandbox, startup fails rather than silently retrying without one. Browser launch flags attempting `--no-sandbox` or `--disable-setuid-sandbox` are rejected while sandboxing is required. A legacy caller must explicitly opt out with `chromium_sandbox=False`; this removes a major defense and is not approved for untrusted content or network-exposed services. Remote CDP browser sandboxing is controlled by the separate browser host, not by this client-side flag.

An owned-loopback test with the reviewed local Chromium binary successfully rendered a JavaScript-updated page under the enabled browser sandbox. This is **not** network isolation or comprehensive browser security acceptance: sandbox effectiveness, unsupported OSes, browser downloads, filesystem/network policy, CDP sessions, proxy settings, malicious content, and end-to-end SSRF controls remain unverified. Do not run untrusted pages or production scraping until those boundaries are assessed and accepted.

## MCP transport safety (development)

MCP (Model Context Protocol) is **optional**. After reviewing the optional dependencies, install `.[ai]`; the branded `goreecloud-web-scraper-mcp` command retains the original `scrapling-mcp` compatibility alias. The default stdio transport does not open a TCP listener.

Streamable HTTP is **authenticated by default**. Prefer `SCRAPLING_MCP_AUTH_TOKEN` over a CLI token argument, since command arguments can appear in process listings. Without a token, `--http` refuses to start. The explicit `--no-auth` opt-out is permitted **only on a loopback bind**, and Host/Origin restrictions are enforced. Non-loopback bindings require both an authentication token and an explicit `--allowed-host` list. HTTP itself is not encrypted: if a private remote endpoint is needed, use trusted TLS termination, network isolation and firewall policy. The original environment-variable spelling remains for compatibility.

**Served MCP destination authorization:** The official MCP runner now defaults to **no approved target origins**, so HTTP fetch tools cannot make outbound requests until a trusted operator supplies exact `--allowed-target-origin` values. Each approved origin includes scheme, hostname, and effective port (for example `https://example.org` or `http://127.0.0.1:8123`); there are no wildcards or implicit subdomains. URLs with embedded credentials, misleading authorities, or fragments are rejected. The server checks current DNS answers and rejects private, loopback, reserved, and link-local IPs by default. The supported served MCP HTTP path then **pins the chosen validated IP into libcurl with CURLOPT_RESOLVE** and disables inherited HTTP_PROXY/HTTPS_PROXY/ALL_PROXY environment routing for each request, including persistent session requests; HTTP/3 is not yet qualified and is blocked for served requests. `--allow-loopback-targets` permits specifically allowlisted loopback destinations **only when the MCP listener itself binds to loopback**, for development fixtures. It never authorizes RFC1918 LAN addresses.

For served MCP **HTTP** requests, automatic redirects are disabled, a caller's request to enable them is refused, and client-supplied proxies, unsafe Host/routing overrides and TLS verification bypasses are blocked. The original Python Scrapling fetcher API is deliberately unchanged. Browser MCP tools are disabled in the official runner by default: browser clicks, JavaScript, subresources, redirects and remote CDP need separate confinement. `--unsafe-allow-browser-tools` is a deliberate legacy opt-in **limited to loopback MCP listeners**; this opt-in is unsuitable for untrusted clients or production.

Example for a **local test fixture only**, with the listener bound to localhost and no unauthorized targets: `goreecloud-web-scraper-mcp --http --host 127.0.0.1 --no-auth --allowed-target-origin http://127.0.0.1:8123 --allow-loopback-targets`. The external service, if ever configured, still requires a bearer token, an MCP `--allowed-host` allowlist and a trusted TLS reverse proxy; that listener Host/Origin setting is **not** the target-origin allowlist.

**Served MCP HTTP resource bounds (development):** Requests submitted through the official MCP runner use a maximum **1 MiB outbound form/JSON body** and **4 MiB decoded HTTP response body** enforced by libcurl (fixed-length, chunked and gzip are tested), plus a post-fetch body-length check before extraction; a request timeout must be **0.1–30 seconds** (30 seconds by default); retries are forced to **one attempt**, and automatic redirects remain disabled. Excess responses fail closed rather than returning partial extracted content. These limits apply only to the supported served MCP HTTP path, not to arbitrary direct-library scraper use or unrestricted browser tools. They do not constitute a complete inbound MCP message/header/cookie-size, DNS-preflight, rate-limit, extraction-output, compressed-payload, concurrent-session or total job-duration quota.

**Installed dependency license-file evidence (development, unreviewed):** A read-only Python standard-library script now enumerates candidate license/NOTICE/COPYING files explicitly listed in installed distributions' manifests, verifies bounded regular files within their installation root and records relative filenames, byte lengths and SHA-256. The current isolated 70-package MCP environment yielded **104 recorded license/notice artifacts** across all 70 packages, with no missing *file-presence* evidence at that point. Two runs matched byte-for-byte. Hosted CI runs offline tests and a nonpublishing deterministic hash-only inventory. This **does not determine license compatibility**, SPDX identifiers, actual upstream source/license coverage, runtime browser/OS licenses, full optional-extras closure or signing and production release authorization. See [security release gate #3](https://github.com/GoreeCloud/web-scraper/issues/3).

**GitHub Actions supply-chain guardrail (development):** The only active CI workflow now pins actions/checkout and actions/setup-python to the exact SHA-1 Git commits resolved from their official GitHub v6 tag refs on November 8, 2026. The script scripts/check_workflow_action_pins.py and its offline negative tests reject unreviewed/movable workflow action references; the static integrity job enforces the policy on PRs. These source pins stop automatic movement of major-version tags but **do not audit GitHub Actions source, sign build provenance, lock Python transitive dependencies, or guarantee safe hosted runners**. Future action changes require a new reviewed commit pin and policy update.

**Reproducible development dependency snapshot (license review incomplete):** `scripts/generate_dependency_inventory.py --output /path/to/installed-environment-cyclonedx.json` emits a sorted CycloneDX **1.5 metadata-only** inventory of Python distributions installed in the invoking environment, including package names/versions, recorded License-Expression or classifier labels where available, and a SHA-256 of any legacy License metadata without reproducing long license text. The code uses only the Python standard library, does not import the enumerated packages or call package indexes, and does not include secrets or local filesystem paths. The optional MCP CI job verifies deterministic same-environment output, reports its SHA-256 and count of missing license metadata, and discards its ephemeral JSON on exit. This is **not** a resolved optional-extras dependency graph, locked transitive closure, complete source-code/license audit, security certification, signed SBOM, public release or deployable artifact; incomplete/missing labels are review findings, not permission to distribute software.

**Official MCP HTTP header budget (development):** The installed MCP SDK's streamable-HTTP ASGI app is wrapped with a minimal, source-controlled **8 KiB / 64-field inbound HTTP header budget**. Requests over either threshold receive a generic **431** before MCP authentication or tool dispatch; bearer tokens/cookies are not reflected in the error. The middleware does not consume the request body, and stdio/direct-library behavior is unchanged. An owned-loopback wheel-installed HTTP listener verified oversized bytes, excessive fields and successful authenticated recovery. These **ASGI scope** checks are defense-in-depth: they do not limit raw HTTP parsing before ASGI, slow header uploads, socket/file-descriptor occupancy or kernel/network egress.

**Official MCP HTTP transport ingress quotas (development):** The official HTTP listener uses its installed MCP SDK's built-in request-body/session manager limits: **256 KiB maximum inbound MCP request body** (413 for both oversized declared-length and chunked bodies, before parsing), **8 concurrent MCP protocol sessions** (503 on excess initialization), and **300-second idle eviction** when no request is in flight. These transport protocol sessions are separate from the application's limit of eight reusable HTTP/browser sessions; existing sessions can close to reopen admission. A rebuilt-wheel, authenticated disposable loopback listener passed the 413 and protocol-cap/refill tests. The separate 8 KiB/64-field ASGI header guard does not bound slow uploads, parser work before ASGI, open socket/FD count, outbound curl effects, or stdio. No external service or public listener is approved.

**Official served MCP cooperative full-operation deadline (development):** A served static HTTP tool has an additional **35-second asyncio operation budget** including destination authorization/DNS-await, transfer, and response extraction, not merely a per-request curl timeout. Deadline expiry is reported as a tool error, and the concurrency admission slot is released after cancellation processing. The implementation uses Python 3.10-compatible cooperative `asyncio.wait_for`; it **cannot preempt blocking CPU work, forcibly kill a stuck native library, guarantee that underlying DNS threads are aborted, or enforce kernel/network isolation**. This guard applies to the supported official served MCP path, never to ordinary direct Python/SDK use.

**Official served MCP static HTTP request-rate, metadata and extraction-output bounds (development):** A single MCP process now admits up to **60 static HTTP tool attempts in a sliding 60-second window** across one-shot/persistent calls (denied targets also count), with **32 KiB total JSON-encoded request metadata** (query parameters, headers, cookies and basic-auth fields) and **256 KiB maximum serialized extracted response**. Requests exceeding those limits fail rather than returning silently truncated content; a consumed rate token is not refunded after a later denial or cancellation. Existing 4 concurrent served HTTP calls, 8 sessions, 4 MiB decoded response and 1 MiB outbound-body limits remain. These limits do **not** enforce robots.txt, target-specific rate policy, consent, tenant quotas, strict uninterruptible CPU/native/process deadlines, inbound HTTP headers or network/process isolation. Before any real website collection, review [privacy, authorization, retention, and site-access obligations](docs/MCP_PRIVACY_AND_OPERATIONS.md); this development MCP transport is not approved for public production exposure.

**Official served MCP session/admission bounds (development):** At most **8 active or starting reusable sessions** share one official MCP server instance, including browser sessions if their explicitly unsafe loopback opt-in is used. Session admission reserves a slot before asynchronous startup, fails closed when full, and frees reservations on startup cancellation or failure; closing a session frees capacity. At most **4 concurrent served static HTTP tool calls** share a semaphore across one-shot and reusable-session requests; additional calls fail with an explicit tool error after **0.25 seconds** of admission wait. Cancellation releases the HTTP admission slot. These limits are **per process**, not per user or tenant, and do **not** implement per-tenant or cluster-wide quotas, comprehensive HTTP-header or slow-client limits, complete transport cancellation safety, or global CPU/memory limits. They do not change the ordinary direct-library Scrapling fetchers and are only activated through the official served MCP transport.

**Real owned-loopback MCP acceptance (development):** The dedicated `tests/goreecloud/test_mcp_live_listener.py` test exercises the wheel-installed branded MCP CLI as a separate subprocess bound to `127.0.0.1` only, with a generated bearer token passed through a minimal environment (never the CLI argument list), and no public scraping. It tests HTTP auth refusals, incoming Host/Origin restrictions, a real authenticated MCP client that fetches only a disposable local target, redirect non-follow, target-allowlist denial, disabled browser operations, persistent-session closure and process cleanup. This development test is part of the MCP CI job; it does **not** validate remote TLS, production identity, OS-level egress confinement, privacy policies or a deployed service.

**Remaining security gate:** The reviewed curl_cffi transport now uses a pinned, validated destination IP for served MCP HTTP requests, reducing DNS-rebinding exposure. This is still **not** a formal guarantee of complete SSRF prevention or a public-facing service approval: custom SDK adapters, transport upgrades, pooled-connection/HTTP-version interactions, other proxies or browser/CDP subresources and unusual host OS networking require separate review. Outbound firewall/network-namespace enforcement, rate/response-size limits, credential controls and private-data rules remain required. The direct Python `ScraplingMCPServer` / custom SDK adapter, when used without the supported `serve()` runner, retains upstream behavior and is not an externally safe hosting interface. Do not expose it to untrusted callers. CI checks MCP target validation and fixture HTTP behavior, but does not perform public-site scraping or arbitrary external access.

## Checkpoint safety (development)

Spider checkpoints are local state stored as `checkpoint.pkl`. The downstream loader now rejects arbitrary pickle classes, checkpoint symlinks, nonregular files, invalid structures, and checkpoint files over 64 MiB. Restored Request records also undergo structural type checks for their URL, session, priority, retry count, callback, metadata, HTTP options and fingerprint fields. Callback names must be ordinary Python identifiers rather than special-method names, and appended data after one complete pickle stream is rejected. The checkpoint file format remains unchanged, allowing ordinarily shaped legacy checkpoints to load. Writes are atomic and create private temporary files (0600 on POSIX). This is defense in depth, not proof that attacker-controlled pickle data is safe. Unsupported/malformed legacy checkpoints deliberately fail closed.

Do not import checkpoint files from another person, share a checkpoint directory with untrusted users, or rely on saved checkpoints for recovery of sensitive production workloads without additional testing. Unsupported legacy object types are deliberately rejected and start fresh. Operators should keep checkpoint directories private, back up any needed prior state, and restrict access to credentials and scraped content.

## Wheel provenance and build reproducibility (development)

A read-only CI gate builds the package wheel twice using an identical environment and fixed `SOURCE_DATE_EPOCH`, compares the resulting bytes, then validates the archive's embedded BSD-3-Clause license against the exact repository `LICENSE`, distribution metadata, original D4Vinci/Scrapling attribution, preserved CLI aliases and every wheel `RECORD` digest. Negative checks must reject a tampered payload and a missing license. The SHA-256 is written to CI logs / job summary; the workflow neither publishes packages nor creates a signed release.

Passing this check establishes **only same-run, same-environment artifact reproducibility and local wheel integrity**. Build-tool versions are not fully locked; no independent builder, cross-platform reproducibility, cryptographic attestation, complete dependency-license/SBOM evaluation or production release approval is implied.
